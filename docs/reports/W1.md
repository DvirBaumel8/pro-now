## Security review note

- **Sessions:** httpOnly cookies. No token is readable by JavaScript and
  there is no bearer path. Signing out, signing out everywhere and deleting
  the account all end sessions on the server.
- **Magic-link tokens:** stored hashed, valid for 15 minutes, usable once.
  A test confirms the token as sent is never in the database.
- **Account linking:** only between verified emails. Google is not a
  trusted provider. A test shows an unverified Google email cannot take
  over an existing account.
- **CSRF and origin checks** are pinned on. Better Auth turns them off
  under `NODE_ENV=test`, and pinning them means the tests exercise the
  production behaviour. Tests cover a cross-site request and an off-site
  callback URL.
- **Every route is covered by a role and an ownership rule.** Another
  person's record answers 404, never 403, so a stranger cannot confirm that
  a record exists.
- **ADMIN** comes only from `ADMIN_EMAILS`, only for a verified email,
  and every grant is audited.
- **Deployed environments refuse to boot** without `AUTH_SECRET` (at least
  32 characters), `RESEND_API_KEY` (or `SMTP_URL`), `EMAIL_FROM`, or a
  non-local `PUBLIC_URL`.
- **Open risks:**
  - No per-email limit on sign-in emails until Phase 3 (docs/21 §4b).
    Better Auth's per-IP limiter is the only protection.
  - The `/v1/*` routes have no CSRF token. They rely on SameSite=Lax
    cookies and the CORS allowlist. That is adequate for same-site
    JSON calls; revisit it if a cross-site client is ever added.
  - Deleting an account needs no recent sign-in. A stolen live session
    could delete the account. Consider a freshness requirement in W10.
